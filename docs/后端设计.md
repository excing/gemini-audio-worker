后端设计

所有代码全新从头写到 `v1` 目录.

本 Worker 是一个 Cloudflare Workers 应用，扮演 **客户端 (浏览器) ↔ Gemini Live API** 的双向 WebSocket 中继 + 工具编排层。入口按 URL 与 `Upgrade` 头分流：

- `/api/tools` → 返回当前可用工具清单。
- 任何 `Upgrade: websocket` 请求 → 升级为 `/ws`，启动 Gemini 桥接。
- 其它请求 → 由 Workers Assets 回退到静态资源。

通过 `run_worker_first` 规则保证 API 与 WS 始终优先命中 Worker，不会被静态资源代理拦截。

# 架构设计

纯 JS 实现, 由 Cloudflare workers 驱动, 不使用包管理器.

## 缓存设计

由 Isolate 作为一级缓存, 保存服务端本地工具列表.

## Libs 设计

libs 设计为通用 JS 模块, 可供前后端共同使用.

### Tool call 定义

工具调用模块, 按运行位置分三类:

- **runtime** — 运行时工具, 每次 setup 都必须注入 Gemini tools 的内置工具 (如 `see_you_later`), 对用户不可见、不可选, 由 Worker 持有声明与处理逻辑.
- **worker** — 服务端本地工具 (`src/tools.js`), 对用户可见可选, 用户在 `autoLoadTools` 选择后随 setup 注入 Gemini, 由 Worker 处理执行.
- **browser** — 浏览器侧工具, 包括前端内置工具 (如 `renderPage`, `codeExecution`) 和**前端配置的 MCP 工具**. 由前端在 `setup.browserTools` 里把扁平 functionDeclarations 提交给 Worker, Worker 不区分来源、不做处理, 直接拼进 Gemini setup 的 tools 数组. Gemini 触发调用时, Worker 把这些 toolCall 透传给前端, 前端自己派发到内置 handler 或 MCP `tools/call`.

注意: MCP 是浏览器侧子能力, Worker 对 MCP 零感知 — 没有 MCP 客户端、没有 MCP server 配置入口、没有 MCP 鉴权.

### Tool call 用户选择

可选 localSetup.autoLoadTools, 按逗号`,`分隔.

- 空值, 表示未选任何可选工具.
- 字符串, 按`,`分隔的 tool name (worker / browser 任一种), 比如`aaa,bbb,ccc`.
- `*`, 表示选择所有可选工具.

Worker 端把这串名字与 worker `toolDeclarations` 求交, 得到要注入的 worker 工具. 浏览器侧 (含 MCP) 的解析、`<server>__<tool>` 前缀展开均在前端完成.

### Tool call 执行

分两种情况

- 服务端(后端)匹配到的工具, 由后端执行 (仅 worker / runtime).
- 客户端(前端)匹配到的工具, 由前端执行 (browser 内置 / MCP).

具体是, 服务端接收 Gemini toolCall 消息后, 先匹配 worker `toolHandlers` 执行, 剩下的不解析直接 forward 给前端, 由前端自己派发.

#### Tool call 执行状态

服务端工具执行状态由服务端发送给客户端, 客户端工具执行状态由客户端自己处理.

### 设计

服务端有两种工具(worker, runtime), 浏览器端有一种统一的"browser"工具实现(内置 + MCP), 本质上都通过 Gemini 的 toolCall 调用.

所以设计, 是可以包装为一个统一的模块, 并对外提供服务.

```public/libs/tools.js
ToolCallRegister {
  register()
  get()
  handler()
}
```

### setup

前端连接 WS 成功后(ws opened), 直接发送 setup(localSetup) 请求, 此请求为本地协议, 而不是 Gemini live setup 协议.

服务端连接 Gemini live 成功后, 组装 localSetup 为 gemini setup 并发送.

# API 接口

## /api/tools

工具调用列表 — 给前端一个 **不依赖** 建立 Live 会话的元信息接口，用于在登录页 / 设置页里渲染「可启用工具」选项。

### 实现方式

- 使用 **Isolate 内的模块级数组** 作为一级缓存. 一个 Isolate 内首次请求才构建一次, 之后直接返回缓存.
- 工具来源: 仅 worker 本地工具声明. **MCP 已下放到前端**, 不在此处暴露; 浏览器内置工具也在前端直接持有, 也不在此处暴露.
- 响应只暴露 `name` 与 `description` 两个字段——参数 schema 等敏感细节留给真正建立 Live 会话时的 `setup` 注入阶段处理.
- HTTP 缓存头 `Cache-Control: public, max-age=300, stale-while-revalidate=600`, 让 Cloudflare 边缘再缓 5 分钟, 过期 10 分钟内仍可 SWR 回源.
- 路径上没有任何远端依赖, 不需要降级分支.

### 请求格式

```
GET /api/tools
```

无请求体、无查询参数、无鉴权。

### 响应格式

成功（200，可被边缘缓存）：

```json
{
  "tools": [
    { "name": "get_weather", "description": "查询 wttr.in 提供的天气信息。" },
    { "name": "web_search",   "description": "联网搜索网页信息..." }
  ]
}
```

仅返回 worker 工具的 `name` / `description`. 前端在 UI 上还会合并:

- 前端内置的 browser 工具声明 (静态写在 `public/tools.js`).
- 当前 role 配置的 MCP 工具 (运行时通过 `public/mcp-client.js` 拉取).

## /ws

实时语音连接 — 单一 WebSocket 同时承载：客户端 → Gemini 的实时音频/文本，以及 Gemini → 客户端的音频/字幕/`toolCall`/`workerStatus`。

### 实现方式

整条链路分为「升级握手 → setup 注入 → 双向消息中继 → 工具编排 → 会话恢复 → 优雅关闭」几个阶段：

1. **WebSocket 升级**：Worker 创建一对 ws（pair），自己持有 server 端，把 client 端通过 101 响应交还浏览器。
2. **启动校验**：必须命中 Worker 绑定的 Gemini API Key。失败时仍然完成 101 升级，但发送一条 `workerStatus.error` 后立即关闭，让前端能收到结构化错误，而不是裸 HTTP 4xx。
3. **会话状态闭包**：单次连接里持有「启用的 worker 工具名集合」, 客户端首次 setup 时回写, Gemini 端有工具调用时读取.
4. **Gemini Live 上游连接**：连接 Gemini 官方 BidiGenerateContent 端点，维护当前 ws 与**单调递增的代数 (generation)**。所有 Gemini 侧事件回调先比对代数，发现自己不是「最新一代」就直接返回，杜绝旧连接回调串扰新连接。
5. **自动会话恢复**：每次发送 `setup` 都会注入 sliding window 上下文压缩与 `sessionResumption` 字段；当 Gemini 推回新的 resumption handle 时缓存下来。收到 `goAway` 或非正常关闭时，按短延迟调度重连，用旧 setup + handle 重连成功后再关闭旧连接，做到平滑替换。
6. **初始消息缓冲**：客户端在 `setup` 中携带的 `initialMessages` 会被暂存，等到 Gemini 回 `setupComplete` 再一次性 flush；避免提前发送被丢弃。
7. **客户端 → Gemini 透传**：除 `setup` 之外的所有客户端消息（音频、文本、`toolResponse`、`clientContent` 等）一律不解析直接转发上行。
8. **Gemini → 客户端**：没有工具调用就原样下发；有工具调用则触发本 Worker 的工具编排（详见「工具调用」一节），结果回填 Gemini 并把浏览器侧工具透传给前端。
9. **关闭传播**：客户端关闭时标记「主动关闭」标志位阻止重连，主动断开上游 Gemini ws。

### 请求格式

ws 帧载荷 = JSON 字符串。首帧 `setup` 是**本 Worker 自有的本地协议**, 与 Gemini Live BidiGenerateContent 的 setup schema 解耦; 服务端会根据本地 setup 重新组装 Gemini setup 并下发. 后续帧仍是 Gemini Live 客户端消息, Worker 不解析直接透传.

首帧（必须, 本地协议）:

```json
{
  "setup": {
    "model": "default",
    "voiceName": "Puck",
    "systemInstruction": "你是一个简洁友好的中文语音助手.",

    "autoLoadTools": "get_weather,web_search,renderPage",
    "browserTools": [
      { "name": "renderPage", "description": "...", "parameters": { /* JSON Schema */ } },
      { "name": "mcp1__list_repos", "description": "...", "parameters": { /* JSON Schema */ } }
    ],
    "initialMessages": [
      { "realtimeInput": { "text": "你好" } }
    ]
  }
}
```

字段说明:

| 字段 | 类型 | 说明 |
|------|------|------|
| `setup.model` | string | 模型别名, 由 Worker 解析为真实的 Gemini 模型 ID, 未匹配走默认值. |
| `setup.voiceName` | string? | 可选语音名, Worker 会包装为 `generationConfig.speechConfig.voiceConfig.prebuiltVoiceConfig.voiceName`. |
| `setup.systemInstruction` | string? | 系统提示词原文, Worker 会包装为 `{ parts: [{ text }] }`. |
| `setup.autoLoadTools` | string | 启用的工具名, 逗号分隔; `*` 表示所有. Worker 与本地 `toolDeclarations` 求交得到 worker 工具; 浏览器侧 (含 MCP) 的展开由前端负责. |
| `setup.browserTools` | array? | 浏览器侧 functionDeclarations 扁平数组 (含前端内置工具与前端解析后的 MCP 工具), Worker 不区分来源, 直接包成 `{ functionDeclarations }` 注入到 Gemini tools. |
| `setup.initialMessages` | array? | Setup 完成后立刻发给 Gemini 的 realtimeInput 序列, 常用于首轮 prompt. |

服务端注入到 Gemini setup 的字段（前端无需关心）: `generationConfig.responseModalities = "AUDIO"`、`inputAudioTranscription`、`outputAudioTranscription`、运行时工具（如 `see_you_later`）、原生工具（如 2.5 模型的 `googleSearch`）、`contextWindowCompression`、`sessionResumption`.

后续帧: 任何合法的 Gemini Live 客户端消息（`realtimeInput` 音频/文本、`toolResponse`、`clientContent` 等）, Worker 不解析直接透传.

### 响应格式

下行帧也是 JSON 字符串，分三类：

**1. Gemini 透传消息** — 原封不动 forward。包括 `serverContent`、`toolCall`、`sessionResumptionUpdate`、`setupComplete`、`goAway` 等。

**2. Worker 注入的状态消息** — 包一层 `workerStatus`，方便前端区分：

```json
{
  "workerStatus": {
    "type": "session_resuming",
    "message": "正在恢复 Gemini Live 会话...",
    "reason": "goAway"
  }
}
```

已使用的 `type` 取值：

| type | 含义 |
|------|------|
| `error` | 不可恢复错误，紧接着会关闭连接。 |
| `info` | 首次连接 Gemini。 |
| `gemini_open` | Gemini ws 首次打开。 |
| `session_reconnect` | 启动重连流程。 |
| `session_reconnected` | 重连成功，setup 已重发。 |
| `session_resuming` | 正在重发 setup（带 handle）。 |
| `session_handle` | 收到新的 resumption handle。 |
| `go_away` | Gemini 通知即将关闭。 |
| `gemini_error` | Gemini 报错或未曾打开就关闭。 |
| `gemini_close` | Gemini 正常关闭（含 runtime 工具主动关闭）。 |
| `warning` | 非致命问题（Gemini 未就绪等）。 |

```json
{
  "systemContent": {
    "toolCall": {
      "id": "fc_xxx",
      "name": "web_search",
      "status": "running",         // running | done | error
      "args": { "query": "..." },
      "response": { /* done/error 时 */ },
      "error": "...",              // error 时
      "startedAt": 1700000000000,
      "endedAt":   1700000000123
    }
  }
}
```

### 状态机

会话由三个相对独立的状态层叠加而成：

```
┌───────────────────────── 浏览器 ↔ Worker ws (server 端) ─────────────────────────┐
│ accept → message... → close                                                     │
└─────────────┬──────────────────────────────────────────────────┬────────────────┘
              │ first setup                                       │ subsequent
              ▼                                                   ▼
┌─────────── setup lifecycle ──────────┐         ┌──── frame forward (透传) ─────┐
│ raw → parse → buildGeminiSetup →     │         │ realtimeInput / toolResponse │
│ managed setup                        │         │ → 上行 Gemini                │
└─────────────┬────────────────────────┘         └──────────────────────────────┘
              ▼
┌─────────────────── Gemini Live ws (Worker → google) ───────────────────┐
│  state = CONNECTING                                                    │
│     ├─ open  → setupComplete? → flush initialMessages                  │
│     ├─ msg.sessionResumptionUpdate → update handle                     │
│     ├─ msg.goAway              → 调度重连                              │
│     ├─ msg.toolCall            → runtime → dispatch → response         │
│     ├─ error                   → notify, 不主动重连                    │
│     └─ close(code)                                                     │
│           ├─ code === 1000 或 client 已关闭 → 终态                     │
│           └─ 其它 + 有 setupMessage + 有 handle → 调度重连             │
│                                                                        │
│  重连：短延迟后用旧 setup + handle 新建连接                            │
│  新连接 open 后:                                                       │
│     1. 复发 setup (带 sessionHandle)                                   │
│     2. 关闭旧连接                                                      │
│     3. 代数 +1，旧连接事件回调自动失效                                 │
└────────────────────────────────────────────────────────────────────────┘
```

关键不变量：

- **代数 (generation) 兜底**：每次新连接都会让代数自增，所有事件回调先判断代数失配就直接返回；旧 ws 即使比新 ws 后关闭也不会污染状态。
- **主动关闭标志位**：客户端关闭后所有 reconnect 路径直接短路，避免「客户端已经走了，Worker 还在自己跟 Gemini 重连」。
- **初始消息只发一次**：单次置位后重连不会重发首批消息——重连依赖 Gemini 侧的 resumption handle 自行恢复上下文。
- **Setup 缓存**：保留客户端首次 setup 的副本，重连时再次套上最新 handle 发出。
